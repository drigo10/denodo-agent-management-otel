# Telemetry behavior

## Collection and export are different layers

The upstream SDK uses LangChain/LangGraph for execution and Langfuse callbacks for tracing. `scripts/bootstrap.py` adds a small initialization branch to choose our exporter. It does not replace the chatbot's model or orchestration code. A Langfuse server is not deployed.

The exporter captures the original readable spans, optionally clones them with added GenAI attributes, captures the mapped payload, then exports OTLP/HTTP protobuf to AM. Local captures represent protobuf messages rendered as JSON; network transport remains protobuf. Neither local file contains the exporter's bearer-authentication header.

`DENODO_AM_EXPORT=1` is generated by the configuration script. `DENODO_AM_NORMALIZE` selects baseline or mapped mode. Reconfiguration requires restarting both Python services.

## Added attributes

| Native evidence | Added compatibility field |
|---|---|
| Generation observation | `gen_ai.operation.name=chat` |
| Parentless chain/agent observation | `gen_ai.operation.name=invoke_agent` |
| Tool observation | `gen_ai.operation.name=execute_tool`, tool name/input/result |
| `session.id` | `gen_ai.conversation.id` |
| Observation input/output | `gen_ai.input.messages`, `gen_ai.output.messages` |
| `langfuse.observation.model.name` | `gen_ai.request.model`, `gen_ai.response.model` |
| `langfuse.observation.metadata.ls_provider` | `gen_ai.provider.name` |
| Usage JSON `input` and `output` | `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens` |

The response-model field uses the model identifier supplied by the native observation; there is no separate verification of a provider-returned model ID. The mapping adds `denodo.am.mapping.version=langfuse-to-genai-v1` to mark its output.

Existing `gen_ai` fields are not overwritten. Original Langfuse fields, `user.id`, trace/span IDs, parents, timing, events, links, resources and status are retained. User identity and usage counts are not synthesized when absent. Retaining original and mapped message fields increases payload size.

## Interpretation limits

- A parentless SDK chain is treated as an invocation for receiver compatibility. This is an integration choice, not a statement that every SDK chain is an independently deployed business agent.
- A question may create several SDK pipeline traces. The receiver may store several interaction rows for that one question. Use conversation identifiers and application context when interpreting volume.
- Nested generic chains stay generic. Only `generation`, `tool`, and parentless `chain`/`agent` observations receive an operation mapping.
- Message mapping produces text message parts. It is not a full multimodal or streaming-event conversion, and it does not preserve tool-call structure in message parts. Original fields remain available for inspection.
- Model/provider recognition, token pricing, cost attribution, error mapping and derived metrics must be verified in the target AM version. Trace retention alone does not prove all of them work.
- This adapter does not repair application-level identity loss. If `user.id` is missing at the source, it remains missing.

## Evidence to compare across environments

Record SDK/framework versions, tracing integration and version, authentication mode, collector transformations, and AM version. Compare a complete raw trace with its parsed dataset row, including service name, root operation, user identity, session/conversation ID, hierarchy, messages, model and token fields. Separate delivery, accepted semantics, retention and downstream dataset builds when diagnosing failures.

## Capture storage

Both files are under ignored `.runtime/sdk/local-data/telemetry`. They include conversation content and can grow over time; there is no built-in rotation in this small adapter. Preserve the original baseline when analyzing the effect of mapping. Do not commit runtime captures to a public repository.
